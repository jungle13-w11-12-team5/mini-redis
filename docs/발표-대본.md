# 발표 흐름 — 미니 레디스 개발 (4분)

> 외워서 말하는 대본이 아니라 흐름 메모다. 각 구간에서 꼭 말할 것과 숫자만 적었다. [그림]은 띄울 캡처(`docs/images/`).

## 한 줄 요약 (처음과 끝에 같은 말)

**차이를 만든 건 레디스의 속도가 아니라, DB가 해야 하는 일의 양이었다.**

---

## 1. 왜 (0:00 – 0:30)

- 미니 레디스를 만들었고, 직접 만든 DB 앞에 붙여서 테스트해 보고 싶었다
- 레디스는 메모리에서 키 하나 찾기, DB는 SQL 해석부터 결과 변환까지 → 그래서 빠르다고 알려짐
- 그런데 요청 하나씩 비교하니 **차이가 거의 없었다** — DB 1.96ms vs 레디스 0.81ms
- DB가 B+트리로 이미 빨랐기 때문 → 그래서 합쳐서 실제 요청 경로로 비교

## 2. 각각 어떻게 만들었나 (0:30 – 1:20)

**레디스**
- 진짜 레디스와 같은 통신 규격, 기초 명령어 구현
- 스레드 하나라 락 없음 — 단, 명령이 짧다는 전제. 길면 나눠서
- 해시 테이블: 4칸에서 시작, 차면 두 배, 요청마다 한 칸씩 옮김

**DB**
- 원래 삽입·조회만 됨 → 캐시 시험하려고 수정 추가
- 변경 사항을 전부 파일 끝에 쌓는 방식 → 돌아가지만 계속 돌리면 파일이 커짐

## 3. 합쳐서 테스트 — 메인 (1:20 – 3:00)

- 구조: 화면 → 웹 서버 → 레디스 먼저, 없으면 DB → 레디스에 저장
- 화면은 미니 리액트 엔진으로 새로 만듦
- **조회를 두 종류로 나눔**
  - id 조회: 인덱스로 1개 찾기 (빠름)
  - 이름 검색: 인덱스 없음, 10만 행 전부 확인 (느림)

[그림 `01-search-miss.jpg` → `02-search-hit.jpg`]
- 빨강 = 레디스, 파랑 = DB
- 이름 검색 처음 20ms, 대부분 파랑(DB) → 다시 하면 2.7ms, 파랑이 사라짐

[그림 `03-call-order.jpg`]
- 줄을 누르면 서버가 한 일이 순서대로 나옴
- 처음: 레디스 확인 → 없음 → DB → 레디스 저장 (4번)
- 두 번째: 레디스 2번으로 끝 (7.8ms → 2.1ms)

- 요청 하나씩 쟀을 때: id는 1.2ms 줄고, **이름 검색은 5.1ms 줄었다** (DB 6.1 → 레디스 1.0)

## 4. 결과와 판단 (3:00 – 3:45)

- 8명이 30초 동안 요청, 3번씩 측정
- **이름 검색 28.8 → 10.7ms, 약 3배 → 의미 있음** (3번 모두 같은 방향)
- id 조회 7.5 → 7.4ms → 의미 없음, DB가 이미 빨라서
- 수정이 1%만 섞여도 캐시 쪽이 더 느림 — 옛 값이 안 남게 수정마다 캐시 전체를 버려서 (적중률 60% → 19%)
- **차이를 만든 건 레디스의 속도가 아니라 DB가 해야 하는 일의 양**

## 5. 실제 서비스 + 마무리 (3:45 – 4:00)

- 실제 서비스는 데이터가 크고 쿼리가 복잡하고 요청이 많아서 캐시 효과가 더 큼
- 캐시는 조회가 오래 걸리고 데이터가 잘 안 바뀔 때 효과가 있었다. 감사합니다

---

## 말할 때 주의

- "DB가 느린 이유는 SQL 처리 때문"이라고 단정하지 말 것. 측정 안 했다. "SQL 해석, 파일 읽기, 결과 변환까지 하는 일이 많다" 정도로
- 숫자는 노트북 CPU 2개 환경이라 흔들린다. "절대값보다 비교로 봐 달라"

## 예상 질문

| 질문 | 답 |
|---|---|
| DB는 정확히 어디서 시간을 쓰나? | 안에서 id 찾는 건 1.9µs. 나머지가 통신·SQL 해석·결과 변환인데, 그중 뭐가 큰지는 따로 안 쟀다 |
| DB만 직접 바꾸면 레디스는 어떻게 아나? | 우리는 모름 → 60초 만료까지 옛 값. 실제 서비스는 DB 변경 기록(binlog)을 읽어 캐시를 지우는 도구(CDC)를 씀. 우리 DB 파일도 변경을 전부 쌓으니 같은 방식을 붙일 수 있다 |
| 왜 바뀐 키만 안 지우고 전체를 버렸나? | 검색 결과 키는 어떤 행이 들었는지 몰라서 못 지움 + 순서가 꼬이면 지운 뒤에 옛 값이 다시 들어감. 버전 번호는 둘 다 해결하지만 캐시 전체를 버리는 대가 |
| 서버가 꺼지면 레디스 데이터는? | 저장 안 함. DB의 복사본이라 다시 채우면 된다 |
| 왜 스레드 하나? | 명령 하나가 짧아서 나눠도 얻는 게 적고, 락이 없으면 동시성 문제가 안 생긴다. 대신 긴 일은 쪼갠다 |
| DB 파일 커지는 건 어떻게? | 옛 행 정리 기능은 안 만들었다. 지금은 측정마다 초기화 |
| 측정 믿을 수 있나? | 3번 재서 같은 방향인 것만 결론으로 씀, 매번 데이터 초기화 |
