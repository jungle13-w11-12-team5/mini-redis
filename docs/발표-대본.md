# 발표 흐름 — 미니 레디스 개발 (4분)

> 외워서 말하는 대본이 아니라 흐름 메모다. 각 구간에서 꼭 말할 것과 숫자만 적었다. [그림]은 띄울 캡처(`docs/images/`).

## 한 줄 요약 (처음과 끝에 같은 말)

**차이를 만든 건 레디스의 속도가 아니라, DB가 해야 하는 일의 양이었다.**

---

## 1. 왜 (0:00 – 0:40)

- 미니 레디스를 만들었고, 직접 만든 DB 앞에 붙여서 테스트해 보고 싶었다
- 레디스 = 메모리에 키-값을 두는 저장소. DB 앞에 캐시로 둔다
- 빠르다고 하는 이유: 하는 일의 양
  - DB: SQL 해석 → 인덱스 검색 → 파일에서 행 읽기 → 결과 변환
  - 레디스: 메모리에서 키 하나 찾기
- 그런데 단순 요청으로 비교하니 **차이가 거의 없었다** — DB 1.96ms vs 레디스 0.81ms
- 이유: DB가 id를 B+트리로 찾아서 이미 빨랐다 (DB 안에서 찾는 시간 1.9µs)
- → 그래서 합쳐서, 실제 요청 경로 전체로 비교해 보기로 했다

## 2. 레디스 구현 (0:40 – 1:30)

- 통신 규격을 진짜 레디스와 같게 → `redis-cli`, Jedis를 그대로 붙여 씀
- 기초 명령어: GET · SET · DEL · EXPIRE · TTL · INCR 등
- **스레드 하나가 명령을 하나씩 실행** → 락이 필요 없음
  - 단, 명령이 짧다는 전제. 길어지면 다른 요청이 전부 기다리니까 나눠서 해야 함
- **해시 테이블:** 칸 4개로 작게 시작 → 키가 칸만큼 차면 두 배
  - 한 번에 옮기면 서버가 멈추니까, 요청 올 때마다 한 칸씩 옮김
  - 옮기는 동안은 옛 배열·새 배열 둘 다 찾음
- 만료: 읽을 때 확인 + 0.1초마다 20개씩 뽑아서 정리

## 3. DB 수정 기능 (1:30 – 2:00)

- 원래 DB는 파일 하나에 이어서 쓰는 구조, 삽입·조회만 됨
- 레디스랑 합쳐서 테스트하려면 **수정**이 필요했다 (DB가 바뀌면 캐시도 맞춰지는지 봐야 하니까)
- 그래서 변경 사항을 전부 파일 끝에 쌓도록 함 — 수정 = 바뀐 행을 새로 씀, 삭제 = 지움 표시
- 단점: 돌아가긴 하는데 **계속 돌리면 파일이 너무 커짐** → 측정할 때마다 데이터를 초기화해야 했음

## 4. 합쳐서 테스트 (2:00 – 2:50)

- 단순 요청으론 차이가 안 나니까 → 웹 서버 + 화면(미니 리액트 엔진)을 만들어서 실제 요청을 처리
- 조회를 두 종류로 나눔
  - id 조회: 인덱스로 바로 찾음 (빠름)
  - 이름 검색: 인덱스 없음, 10만 행 전부 확인 (느림)

[그림 `02-search-hit.jpg`]
- 빨강 = 레디스, 파랑 = DB 시간
- 이름 검색 처음 20ms (DB까지) → 다시 하면 2.7ms (레디스), 파란 막대가 사라짐

## 5. 결과 (2:50 – 3:30)

- 8명이 30초 동안 요청, 3번씩 측정
- **이름 검색: 28.8ms → 10.7ms, 약 3배**
- **id 조회: 7.5ms → 7.4ms, 차이 없음**
- 수정이 1%만 섞여도 캐시 켠 쪽이 더 느림 — 옛 값이 안 남게 수정마다 캐시 전체를 버려서 (적중률 60% → 19%)

## 6. 유의미했나 + 실제 서비스 + 마무리 (3:30 – 4:00)

- 이름 검색은 유의미 — 3번 모두 같은 방향
- id 조회는 의미 없음 — 처음 단순 비교 때와 같은 이유, DB가 이미 빨라서
- **차이를 만든 건 레디스의 속도가 아니라 DB가 해야 하는 일의 양**
- 실제 서비스는 데이터가 메모리보다 크고, 쿼리가 복잡하고, 요청이 수천 개라 DB가 할 일이 훨씬 많음 → 캐시 효과가 더 큼
- 수정할 때도 실제로는 바뀐 키만 지워서, 우리처럼 수정 1%에 무너지지 않음
- 캐시는 조회가 오래 걸리고 데이터가 잘 안 바뀔 때 효과가 있었다
- 감사합니다

## 말할 때 주의

- "DB가 느린 이유는 SQL 처리 때문"이라고 단정하지 말 것. 측정 안 했다. "SQL 해석, 파일 읽기, 결과 변환까지 하는 일이 많다" 정도로
- 숫자는 노트북 CPU 2개 환경이라 흔들린다. "절대값보다 비교로 봐 달라"

## 예상 질문

| 질문 | 답 |
|---|---|
| DB는 정확히 어디서 시간을 쓰나? | 안에서 id 찾는 건 1.9µs. 나머지가 통신·SQL 해석·결과 변환인데, 그중 뭐가 큰지는 따로 안 쟀다 |
| 서버가 꺼지면 레디스 데이터는? | 저장 안 함. DB의 복사본이라 다시 채우면 된다 |
| 왜 스레드 하나? | 명령 하나가 짧아서 나눠도 얻는 게 적고, 락이 없으면 동시성 문제가 안 생긴다. 대신 긴 일은 쪼갠다 |
| DB 파일 커지는 건 어떻게? | 옛 행 정리 기능은 안 만들었다. 지금은 측정마다 초기화 |
| DB만 직접 바꾸면 레디스는 어떻게 아나? | 우리는 모름 → 60초 만료까지 옛 값. 실제 서비스는 DB 변경 기록(binlog)을 읽어 캐시를 지우는 도구(CDC)를 씀. 우리 DB 파일도 변경을 전부 쌓으니 같은 방식을 붙일 수 있다 |
| 왜 바뀐 키만 안 지우고 전체를 버렸나? | 검색 결과 키는 어떤 행이 들었는지 몰라서 못 지움 + 순서가 꼬이면 지운 뒤에 옛 값이 다시 들어감. 버전 번호는 둘 다 해결하지만 캐시 전체를 버리는 대가 |
| 버전 방식 단점은? | 행 하나만 바뀌어도 캐시 전체가 버려짐 → 수정 1% 결과가 그 대가 |
| 측정 믿을 수 있나? | 3번 재서 같은 방향인 것만 결론으로 씀, 매번 데이터 초기화 |
