- "서버가 다운되는 상황 … (Optional)" → 영속성은 할지부터 정함 (Q14)

## 통합 제약 (2026-11-18, 두 저장소 코드 점검)
지도에 알려주기로 올린 것과 같다. 근거만 여기에 적는다.
1. SQL 인젝션: 데모가 `WHERE name = '<입력>'`을 문자열로 만든다. DBMS 문법은 `''` = 작은따옴표 하나(architecture §6.1) → Q27
2. 벤치 기준선이 흔들림: UPDATE는 덧붙이기라 레코드가 흩어지고 전체 스캔이 행마다 따로 읽기로 느려진다(§19). "캐시 끔"이 회차마다 나빠진다 → Q28
3. 결과 크기: 레디스 값 상한 16MB(`RespParser.MAX_BULK`), 송신 1MB 넘으면 배압(ADR-0003). 같은 이름이 많으면 닿는다 → Q29
4. 레디스는 인증이 없고 모든 주소에서 받는다(`Main`: `InetSocketAddress(port)`) → Q26에 포함
5. NDJSON은 스트리밍 도중 실패하면 마지막 줄이 `ok:false` → Q16 규칙을 테스트로 고정(C4)
6. 둘 다 1초 fsync라 서로 다른 것을 잃을 수 있다(DB 쓰기 vs 레디스 INCR) → Q13 규칙(시작 때 INCR) · Q14

### Q10. 데모 화면 · API 범위
- 첫 카드(API만, 2026-11-18): A id 조회만 / B id + 이름 검색 / C B + 요약 집계, 추천 B. 사람이 웹 화면 요구를 더해 아래로 다시 씀
- "레디스 · DB를 각각 부르는 걸 보여 준다"를 둘로 나눔: (1) 추적 — 캐시 경유 API가 안에서 무엇을 불렀는지 단계별 시간 (2) 직접 호출 창 — 캐시 로직을 우회해 레디스 · DB를 직접 건드림. 브라우저는 RESP를 못 쓰므로 둘 다 데모 서버를 거침
- A: id 조회 + 추적 + 직접 호출 창 → 작음. 캐시 효과가 작게 보이고 무효화는 키 하나 지우기뿐
- B: A + 이름 검색(전체 스캔) + 쓰기 두 길(API 경유 = DB 수정 후 무효화 / DB 직접 = 레디스 모름 → 옛 값) + 캐시 켬 · 끔 스위치 → 이득(비싼 조회)과 어려움(어느 키가 낡았나 · 무효화를 빠뜨리면)이 한 화면에
- C: B + 화면 안 작은 부하(버튼 하나로 100회 평균) → 발표 때 바로 비교. 정식 측정이 아니라 숫자를 오해할 위험
- 추천: B. C는 나중에 붙여도 구조가 안 바뀜
- 답: B · 사람 · 2026-11-18
- 이름: cache-aside 데모 + 요청 추적(trace) + 직접 호출 콘솔
- 따라오는 것: 같은 이름이 많으면 결과가 1MB를 넘어 레디스 배압(ADR-0003) 경로를 탐 → C4 엣지에 포함

### Q13. 무효화 방식 (Q10-B 기준)
- A: TTL만 → 코드 0줄. TTL(예 60초) 동안 옛 값이 그대로 나감
- B: DB 쓰기 성공 후 그 키를 DEL + TTL 안전망 → id 조회는 바로 반영. 검색 결과 키는 무엇을 지울지 몰라 TTL에 기댐. 그리고 "miss로 옛 값을 읽던 요청이, 쓰기 + DEL이 끝난 **뒤에** SET" 하면 옛 값이 TTL까지 남음(경합 창)
- C: 테이블 버전 번호 → 레디스에 `users:ver`를 두고 쓰기마다 DB 쓰기 성공 후 INCR. 읽기는 먼저 ver를 읽고 키에 넣음(`users:v8:name:kim`). 쓰기 한 번에 그 테이블 캐시가 전부 낡은 키가 되므로 검색 결과도 한 번에 무효화. 위 경합에서도 늦게 온 옛 값은 아무도 안 읽는 옛 버전 키에 써져 해가 없음. 대가: 요청마다 레디스 왕복 1번 추가, 쓰기가 잦으면 hit 비율이 떨어짐, 옛 키는 TTL까지 메모리에 남음
- D: 섞기 — id 키는 B(DEL), 검색 키만 C(버전) → 쓰기가 잦아도 id 캐시는 살아남아 hit 비율이 가장 높음. 두 방식을 다 구현 · 테스트하고, id 키에는 B의 경합 창이 남음
- 버린 것: 지연 이중 삭제(DEL 후 수백 ms 뒤 한 번 더) → 지연 시간을 짐작으로 정해야 하고 확률적으로만 막음
- 모든 안 공통: DB 직접 수정(Q10-B 화면)은 어떤 방식도 못 잡음 → TTL이 마지막 안전망. DB 쓰기 성공 후 레디스가 죽어 DEL · INCR이 실패해도 TTL까지 옛 값
- 추천: C. Q10-B의 "어느 키?" 문제와 경합 창을 같은 장치로 닫고, Phase 1의 INCR(원자적, Q3-A)을 그대로 씀. 경합 재현 테스트로 B와 C를 나란히 보여 줄 수 있음
- 답: C · 사람 · 2026-11-18
- 이름: 세대 번호 무효화 (generation / namespace versioning)
- 따라오는 규칙:
  - 쓰기 순서는 **DB 쓰기 성공 → INCR**. 반대면 INCR 직후 · DB 반영 전에 읽은 요청이 옛 값을 새 버전 키에 넣어 TTL까지 남음
  - `users:ver`에는 기간을 붙이지 않는다. 없으면 0으로 읽음(INCR은 없으면 1을 만듦)
  - TTL은 신선도가 아니라 옛 키 회수 + DB 직접 수정 안전망. 짧을수록 메모리↓ · 직접 수정 노출↓, 쓰기가 드문 때 hit↓
  - 남는 창: DB 쓰기와 INCR 사이(레디스 왕복 1번)에 온 읽기는 옛 버전의 hit를 받음. 한 번 왕복 길이로 상한
  - Q14와 엮임: 명령 로그로 복구하면 마지막 fsync 뒤의 INCR이 사라져 ver가 되돌아갈 수 있음 → 그 사이 DB가 바뀌었으면 옛 버전 키가 다시 살아남. 데모 서버 시작 때 INCR 1번으로 막음 (Q14 카드에서 확인)

### Q11. DBMS를 가져오는 방식
- 전제: 지금 DBMS 저장소에는 태그가 없고, Dockerfile은 개발용(빌드 도구만)이다. 어느 쪽이든 DBMS 저장소에 **태그 + 실행용 이미지(release 빌드)**가 하나 더 필요하다 (DBMS 쪽 작업)
- A: compose가 옆 폴더 `../미니DBMS`를 빌드 → 가장 단순. 두 저장소가 나란히 있어야 하고, 이 저장소만 clone하면 안 돌아감. 버전 고정은 사람이 지켜야 함
- B: git submodule로 DBMS 태그를 고정 → `git clone --recursive` 한 번이면 `docker compose up`. 고정한 커밋이 저장소에 기록됨. submodule 갱신 명령을 알아야 함
- C: DBMS가 태그마다 이미지를 레지스트리(GHCR 등)에 올리고 compose는 이미지 태그만 씀 → 이 저장소가 가장 가볍고 버전이 명확. 원격 저장소 · 레지스트리 · 올리는 절차가 필요(지금 두 저장소 모두 원격 없음)
- 추천: B. 공개 포트폴리오를 받은 사람이 명령 두 줄로 재현할 수 있고, 지금 없는 원격 · 레지스트리에 기대지 않음

### Q14. 영속성
- 짚을 점: 이 데모에서 레디스는 **캐시**라 원본은 DB에 있다. 잃어도 다시 채울 수 있다. 진짜 손해는 재시작 직후 캐시가 비어 요청이 전부 DB로 몰리는 것(cold start)이다
- A: 안 함 → 범위가 줄어듦. 발표에서 "캐시는 잃어도 되는 데이터"와 cold start 측정 한 장으로 답
- B: 명령 로그 — 쓰기 명령을 실행 직후 RESP 그대로 파일에 덧붙이고, 별도 스레드가 1초마다 fsync, 시작할 때 다시 실행 → 최대 1초 손실(DBMS와 같은 맞바꿈), 파서 재사용(Q1 카드). 만료는 절대 시각으로 바꿔 적어야 재시작 때 기간이 다시 늘지 않음. 로그가 계속 커짐(줄이기는 범위 밖). server에 패키지 하나 추가 → ADR-0004
- C: 스냅샷 → Java는 fork가 없어 실행 스레드에서 전체를 훑어야 함 = Q3-A 규칙 위반. 나눠 찍기는 rehash 중 일관성 규칙이 새로 필요
- 추천: B. 중점 5에 코드로 답하고, cold start vs 로그 복구 후 시작을 bench에 한 줄 더해 "왜 캐시에도 영속성이 의미가 있나"를 숫자로 보여 줌
- 답: 이번엔 안 함 · 위임 · 2026-11-18 — 시간. 발표에서는 명령 로그 설계(B)와 Q13 세대 번호 되돌아감 분석으로 답한다
- 이름: (고른 뒤) AOF (append-only file), everysec fsync
